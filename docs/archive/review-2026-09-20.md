## 三、代码框架审查：仍存在的问题

### 3.1 P2-1：批量根求值未实现（性能，最大瓶颈）

**文档承诺**：§6.2 第 1 步要求"批量根求值（SIMD Batch Root Evaluation）"——将全部根的支持集拼成大扁平数组，一次 `np.searchsorted` 完成批量求值。

**代码现状**：`search.py:199-214`（开放检索）与 `search.py:110-144`（身份检索）仍是 Python 循环逐根调用 `build_query_context` + `peak_bound`。

**实测影响**（2000 谱库，32 棵树，positive ion_mode 开放检索）：

```
row=52:   bound=13.8ms  exact=1.4ms   (bound 占 91%)
row=1704: bound=23.7ms  exact=3.4ms   (bound 占 87%)
row=363:  bound=2.2ms   exact=0.7ms   (bound 占 76%)
```

单次根包络求值 ~49 µs（review 文档实测），其中固定开销主导：每次求值约 10~12 个 NumPy 小数组调用。`_support_spans` + `_expand_spans` 对每个节点重算，而查询侧的 `cell_lower`/`cell_upper` 已提出循环，真正随节点变化的只有 `support` 数组。

**可兑现的优化**：把全部根的支持集拼成一个大扁平数组 + 每根偏移数组，用一次 `np.searchsorted` + `np.maximum.reduceat` 分段聚合完成批量求值。预期开放检索 17~50 ms → 3~8 ms（review 文档 §5.6 估算）。

**规模外推**：开放检索根扫描是 O(M) 且每次查询重扫全部根。M 随库线性增长：16,106 谱 251 棵树 → 17.6 ms；160,000 谱 ~2,500 棵树 → ~176 ms。要打断这个线性关系需要第三层摘要或批量化。

## 四、Benchmark 审查：离子模式配置 Bug（Critical）

### 4.1 问题

`cli.py` 的 `cmd_benchmark` 在构造所有 `QueryConfig` 时**未设置 `ion_mode`**，默认 `IonMode.UNKNOWN` + `IonModePolicy.INCLUDE_UNKNOWN`。

涉及位置：
- `cli.py:140-144`：consistency 身份检索 `QueryConfig`（无 `ion_mode`）
- `cli.py:151-156`：consistency 身份检索动态窗口 `QueryConfig`（无 `ion_mode`）
- `cli.py:169-173`：consistency 开放检索 `QueryConfig`（无 `ion_mode`）
- `cli.py:194-198`：throughput 身份检索 ±0.5 Da `QueryConfig`（无 `ion_mode`）
- `cli.py:206-210`：throughput 身份检索 ±2.0 Da `QueryConfig`（无 `ion_mode`）
- `cli.py:218-221`：throughput 开放检索 `QueryConfig`（无 `ion_mode`）

### 4.2 后果链

`sample_query_spectra` 抽样的查询谱几乎全是 `positive`（GNPS-LIBRARY 中 13,761 positive / 2,345 negative，2,000 谱子库实测 1,695 positive / 293 negative / 0 unknown）。

`UNKNOWN` 查询在 `INCLUDE_UNKNOWN` 策略下的过滤行为：

```
ion_mode_passes(UNKNOWN, INCLUDE_UNKNOWN, POSITIVE) = False
ion_mode_passes(UNKNOWN, INCLUDE_UNKNOWN, UNKNOWN)  = True
ion_mode_passes(UNKNOWN, INCLUDE_UNKNOWN, NEGATIVE) = False
```

即：**UNKNOWN 查询只能匹配 UNKNOWN 分区的谱**。而 2,000 谱子库的 UNKNOWN 分区为空（`n_spectra=0`）。

**JETF 侧**：`search_forest` 的 `eligible_partitions` 为空列表，两个模式的分区循环都不执行，0 次节点求值、0 次精评、0 命中。实测：

```
row=1281: nodes_visited=0, roots_pruned=0, n_scored=0, hits=0, total=0.114ms
row=738:  nodes_visited=0, roots_pruned=0, n_scored=0, hits=0, total=0.041ms
row=362:  nodes_visited=0, roots_pruned=0, n_scored=0, hits=0, total=0.026ms
```

**matchms 侧**：`is_eligible` 遍历 2,000 条谱全部返回 `False`，不打分。耗时 ≈ 0.67 ms（2,000 次 `is_eligible` 调用）→ QPS ≈ 1,400。

**报告数字的含义**：

| 报告数字 | 真实含义 |
| :--- | :--- |
| JETF QPS 29,334 / 35,096 / 40,502 | 空库检索的耗时（几乎无工作） |
| matchms QPS 1,383 / 1,480 / 1,360 | `is_eligible` 遍历 2,000 条谱的固定开销 |
| 加速比 21.2× / 23.7× / 29.8× | **完全没有意义** |
| Recall@K = 100.00% | 双方都零命中，vacuous truth |
| 零漏检 PASS | 双方都零命中，vacuous truth |
| 包络剪枝率 100.0% | `avg_pruned_ratio = 1.0 - 0/N = 1.0`，数学上正确但语义上误导 |

### 4.3 实证验证

将 `ion_mode` 改为 `IonMode.POSITIVE` 后，开放检索立刻恢复正常：

```
row=52:   nodes_visited=132, roots_pruned=8,  n_scored=36, hits=10, bound=13.8ms
row=1704: nodes_visited=51,  roots_pruned=23, n_scored=17, hits=10, bound=23.7ms
row=363:  nodes_visited=56,  roots_pruned=22, n_scored=38, hits=10, bound=2.2ms
```

### 4.4 修复建议

1. `cli.py` 中所有 `QueryConfig` 构造点增加 `ion_mode=meta.ion_mode`（对每条 query 动态设置）。
2. 考虑到 `evaluate_retrieval_consistency` 和 `benchmark_retrieval_throughput` 只接收一个 `config`，需要改为接收"每条 query 独立 config"的列表，或在这两个函数内部根据 query 的 meta 动态生成 config。
3. 在 `benchmark_retrieval_throughput`/`evaluate_retrieval_consistency` 入口断言：当 `config.ion_mode == IonMode.UNKNOWN` 且 `config.ion_mode_policy == IonModePolicy.INCLUDE_UNKNOWN` 时给出警告（"UNKNOWN 查询在 INCLUDE_UNKNOWN 策略下只能匹配 UNKNOWN 分区，可能导致空结果"）。
4. 修复后重新生成 `docs/benchmark-matchms.md` 的全部检索数字。

## 五、Benchmark 审查：次要问题

### 5.1 身份检索的前体窗口语义不符合真实场景

`cli.py:147-157` 注释说"每条 query 动态设置"，但 `evaluate_retrieval_consistency`（`consistency.py:117`）只接收一个 `config`，实际传入的是第一条 query 的窗口（`id_queries_with_cfg[0][2]`）。所有 query 共享同一个前体窗口。

**影响**：JETF 和 matchms 用同一窗口所以对比仍公平，但检索场景不是真实的身份检索（真实场景中每条 query 用自己的前体 m/z），代表性打折。throughput benchmark 同样如此（`cli.py:193` 用 `queries[0]` 的前体 mz）。

**修复建议**：`evaluate_retrieval_consistency` 和 `benchmark_retrieval_throughput` 的签名改为接收 `Sequence[tuple[int, SpectrumPeaks, QueryConfig]]`，或在内部根据 query meta 动态生成窗口。

### 5.2 `rank_consistent` 的平局破并列规则不一致

- JETF 排序键：`(score, external_id, spectrum_index)`（`results.py:31-33`）
- matchms ground truth 排序键：`(score, row)`（`consistency.py:163`）

当 `external_id` 字典序与 row 顺序不一致时，平分场景下 `rank_consistent` 会误报 `False`。

**影响**：该字段未在报告中展示（`format_retrieval_consistency_table` 不含此列），影响有限。但如果未来展示，需要统一破并列规则。

### 5.3 微基准的谱对构造有偏差

`cli.py:112-120` 的 `pairs` 构造：
- 5 组自匹配（`q, q`）→ 分数恒为 1.0，拉高一致性指标平均值
- 1,000 组随机库谱对 → 大多不相交（分数为 0），稀释误差分布

**影响**：MAE = 1.26e-07 看起来极小，但其中大量谱对的真实差异就是 0（不相交）。这会使 MAE/RMSE 比实际高相似谱对的差异看起来更好。

**修复建议**：分层抽样——高相似对（前体窗口内）、中等相似对、不相关对各占一定比例，分别报告误差分布。

### 5.4 微基准的 matchms 计时口径

`scorer.pair(s1, s2)` 返回 dict，取 `res["score"]` 有额外 Python 开销；而 JETF 的 `score_greedy_cosine` 返回 dataclass。这个偏差方向是保守的（低估 matchms 速度），不影响结论方向，但值得注意。

## 六、Benchmark 审查：可信的部分

以下结论不受离子模式 bug 影响，可以信任：

### 6.1 单对谱评分等价性 — ✅ 可信

- **微基准**（§2.1）：`CosineGreedy(tolerance=0.02, mz_power=0.0, intensity_power=1.0)` 的参数映射正确对应 JETF 的线性强度余弦。
- **单元测试**（`test_matchms_scoring.py`）：自匹配、互不相交、部分重叠三个场景均通过。
- **fuzz 测试**：200 组随机谱对（部分重叠 + 噪声扰动），0 组不一致（score 差 < 1e-9 且 n_matched 完全相同）。
- **matchms 归一化行为**：验证了 matchms 内部会除以 `sqrt(sum(I_q²) * sum(I_l²))`，当输入已 L2 归一化时与 JETF 完全一致。

### 6.2 e2e 测试 `test_matchms_retrieval.py` — ✅ 可信

正确使用了 `meta.ion_mode`（`test_matchms_retrieval.py:98,151`），是真正的身份检索零漏检验证。

### 6.3 数据适配器 — ✅ 可信

`jetf_peaks_to_matchms` 的归一化处理正确（默认使用 L2 归一化强度），元数据传递完整（`precursor_mz`、`ionmode`、`charge` 均正确传入 matchms `Spectrum` metadata）。
